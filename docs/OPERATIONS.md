# Exploitation de Sol-0 / Operating Sol-0

*English summary at the end of each section.*

## Le workflow `sol`
- Fichier : `.github/workflows/sol.yml`. Déclencheur : `workflow_dispatch` seulement (plus de `schedule` : c'est le serveur qui fait vivre le rover ; Actions ne sert qu'à `check`, `restore`, `refs`). Ne pas lancer le mode `sol` tant que le serveur vit le rover.
- Modes manuels (`gh workflow run sol.yml -R <propriétaire>/<dépôt> -f mode=<mode>`) :
  - `sol` : un sol (par défaut pour le planning) ;
  - `check` : valide l'état publié, n'écrit rien ;
  - `refs` : calcule les empreintes de référence (imprimées dans le journal du job, entre `REFS-BEGIN` et `REFS-END`, et dans le résumé) ;
  - `restore` avec `-f checkpoint=sol-NNNNNN` (ou `-f checkpoint=schema-N`, voir « Retour au code v1 ») : republie un checkpoint nommé après validation, `epoch + 1` ; ne supprime jamais la branche `state`.
- Ordre de publication : branche `state` (source de vérité), tags, puis `journal/ atlas/ firsts/` sur `main`.
- Codes de `publish.sh` : 0 succès ; 1 rouge après publication (3 sols passifs de suite, ou `main` refusé avec `main_lag` ≥ 2) ; 4 push de `state` impossible après 4 essais ; 5 `state` modifié par un autre écrivain (bail refusé), rien d'autre n'est poussé.
- *EN: manual dispatch only (no schedule: the server lives the rover); modes sol, check, refs, restore; state first, then tags, then main.*

## Réactivation (règle des 60 jours de GitHub)
GitHub désactive les workflows planifiés d'un dépôt public sans activité pendant 60 jours. Décision F1 : **aucun commit vide, aucune réactivation par l'API** ; la seule activité est le vrai produit (commit d'état, commit du journal). Si le workflow est désactivé :
- interface : Actions, `sol`, « Enable workflow » ;
- ligne de commande : `gh workflow enable sol.yml -R <propriétaire>/<dépôt>`, puis `gh workflow run sol.yml -R <propriétaire>/<dépôt> -f mode=sol`.
Condition : aucune protection de `main` qui exige une PR (ou une exception pour `github-actions[bot]`). Sinon le push du journal est refusé : l'entrée reste dans `journal_tail` et le run devient rouge au 3e échec de suite.
La date du dernier contact figure dans `console.gif` et `status.svg`.
*EN: re-enable with `gh workflow enable`; no empty commits, ever (decision F1, to be re-validated by the owner).*

## Restauration
1. Lister les checkpoints : branche `state`, dossier `state/checkpoints/` (5 `sol-*` gardés ; `schema-N` hors rotation, voir plus bas).
2. `gh workflow run sol.yml -R <propriétaire>/<dépôt> -f mode=restore -f checkpoint=sol-000123`.
3. Vérifier le run, puis `status.json` (`det.restored_from`) sur la branche `state`.
Un état corrompu est restauré automatiquement par `rover sol` (checkpoint sain le plus récent, `epoch + 1`). Un état plus récent que le code (schéma, stade) est refusé (code 3) : sortie par `mode=restore` ou par un nouveau code.
*EN: restore with mode=restore and the checkpoint name.*

## Retour au code v1 (schéma 2 vers schéma 1, SPEC 6.14.7, cas 20)
Le premier sol joué par le code v2 sur un état v1 le migre (schéma 1 vers 2) et écrit `state/checkpoints/schema-1.json.gz` (+ `.sha256`) : le core v1, octet pour octet, **hors rotation** (recopié à chaque sol, jamais supprimé par la rotation des 5 `sol-*`). Les blocs de la mémoire d'échantillons (`state/memory/b_<i>.bin.gz`, 256 lignes par bloc, au plus 4 096 lignes) n'existent qu'en schéma 2.
Procédure (l'utilisateur la lance, jamais un agent) :
1. Avec le code **v2** encore sur `main` : `gh workflow run sol.yml -R <propriétaire>/<dépôt> -f mode=restore -f checkpoint=schema-1`. Le run republie le core v1 tel quel (`schema_version` 1, `epoch + 1`, cause `manual`, ligne de journal de restauration), avec les régions explorées, **sans** blocs de mémoire ni checkpoints `sol-*` (ils sont de schéma 2 : un code v1 les refuserait, code 3). Un checkpoint `sol-N` de schéma 1 est écrit par la restauration elle-même.
2. Remettre le code v1 (tag `p1`) sur `main`. Le code v1 charge cet état normalement ; un état v2 donné au code v1 est refusé (code 3, rien d'écrit, jamais de restauration).
3. Vérifier `status.json` (`det.schema_version` = 1, `det.restored_from` = `schema-1`) sur la branche `state`.
Limites : si plus de 5 sols v2 ont tourné, plus aucun checkpoint `sol-*` de schéma 1 n'existe (sortis de la rotation) : le premier sol joué par le code v1 part donc sans checkpoint `sol-*` de schéma 1 (une corruption à ce sol ne serait pas réparable par le code v1). Si l'étape 2 n'a pas lieu, le run v2 suivant re-migre l'état (sans perte, réversible), et réécrit `schema-1.json.gz` à partir du core v1 publié. Les noms acceptés par `rover restore` et par `tools/ci/validate_inputs.py` sont `^(sol-[0-9]{6}|schema-[1-9][0-9]?)$`.
Les échantillons pris par le rover entre la migration et le retour sont perdus pour le code v1 (il ne les connaît pas) ; ils restent dans l'historique de la branche `state`.
*EN: to go back to v1, run mode=restore with checkpoint=schema-1 while the v2 code is on main, then put the v1 code (tag p1) back. schema-1 is kept out of the 5-checkpoint rotation; samples taken after the migration are not carried back.*

## Mémoire d'échantillons (schéma 2)
`state/memory/b_<i>.bin.gz` : bloc i = lignes d'identifiant 256·i à 256·i + 255 ; un sol ne réécrit que le dernier bloc. Au-delà de 4 096 lignes, le bloc le plus ancien est retiré en entier. `state/checkpoints/memory/` garde la version précédente des blocs modifiés ou retirés au dernier sol. Un bloc illisible à la restauration est remplacé par sa copie de garde ; s'il n'y en a pas, il est déclaré perdu dans le journal du chargement (`memory block b_<i> lost`) et jamais reconstitué.
*EN: sample memory blocks, 256 rows each, oldest block evicted above 4096 rows, guard copies in checkpoints/memory.*

## Écrivain extérieur sur `state`
Un commit manuel sur `state` pendant un run fait refuser le bail (code 5, run rouge, rien d'autre poussé). Le run suivant lit l'état modifié et le réécrit : tout fichier ajouté à la main sur `state` disparaît. Ne pas écrire sur `state` à la main.

## Taille du dépôt
`publish.sh` relève `gh api repos/<dépôt> --jq .size` (Ko) : `::notice::` sinon `::warning::` au-delà de `repo_size_alert_kb` (1 048 576 Ko = 1 Go, `config/run.toml`). La valeur renvoyée par GitHub est différée. Parades au-delà de 1 Go : demander un nettoyage au support GitHub, ou espacer les checkpoints. La purge des anciens commits orphelins de `state` prend des semaines (non documentée, non mesurée).

## Direct (serveur `rover live`, kit `tools/server/`)

Cible : Ubuntu 24.04 LTS x86-64 (Contabo Cloud VPS 4 : 4 vCPU, 8 Go ; le kit n'est pas lié à un hébergeur). Tout se lance en root sur le serveur ; sur le Mac, les essais passent par `--root DIR` (actions système simulées).

1. Installer : `sudo tools/server/install.sh --domain EXEMPLE.fr --pages-origin https://LOGIN.github.io --repo LOGIN/DEPOT --sha COMMIT`. Toujours d'abord `--dry-run` : il liste les étapes S1 à S11 sans rien toucher (il annonce moins de changements que l'application réelle, ex. 31 contre 43 : les sous-dossiers ne sont comptés qu'une fois leurs parents créés). Comptes : `sol0` (moteur et publication), `sol0web` (web), groupe `sol0stream`. Relancé, le script rend « 0 changement ». `/etc/sol0/live.toml` n'est créé qu'une fois (`publish = "off"`) : l'utilisateur le modifie ensuite.
2. Jeton : `sudo sol0ctl token set` (saisie masquée, fichier en 0600 dans un dossier 0700 ; l'adresse noreply du propriétaire est lue par `GET /user`). Contrôle : `sudo sol0ctl token check`. Le jeton n'est jamais dans argv, l'environnement, les journaux ni le dépôt.
3. DNS : `A live -> IPv4` (et `AAAA` si IPv6), TTL 300. Caddy obtient seul le certificat. Contrôle : `curl -sSI https://live.EXEMPLE.fr/health`, ou `tools/server/healthcheck.sh`.
4. État : `sol0ctl status` (services, santé, cause), `sol0ctl logs`, `sol0ctl stop|start`.
5. Annuler une installation : `sudo tools/server/rollback.sh <UTC>` (horodatage dans `/var/backups/sol0/`) rend les fichiers, liens et dossiers. Paquets, utilisateurs, pare-feu et services ne sont pas défaits (notés « note » dans `undo.log`).
6. Redémarrage : `sol0-reboot.timer` (15 min) ne redémarre que si `/var/run/reboot-required` existe, le moteur est en phase `idle`, le créneau suivant est à plus de 60 s et aucune publication n'est en attente.
7. SSH par clé seule : posé seulement si `/root/.ssh/authorized_keys` n'est pas vide et si `sshd -t` passe (sinon l'étape est ignorée, avec message).

8. **Naissance : le moteur est retenu.** `install.sh` ne démarre jamais `rover-live` : tant que `/var/lib/sol0/live/birth.json` n'existe pas, un tiroir systemd `rover-live.service.d/00-hold-until-golive.conf` (`ExecCondition=/bin/false`) le garde activé mais arrêté. Seule commande qui le libère, lancée par Diapason avec l'accord de l'utilisateur : `sudo sol0ctl birth --at AAAA-MM-JJTHH:MM:SSZ` (UTC, entre 5 min dans le passé et 1 h dans le futur ; refuse si déjà né, si l'horloge n'est pas synchronisée ou si la date est mal formée ; écrit `birth.json`, retire le tiroir, démarre le moteur). `sol0ctl start` ne démarre que le web tant que le tiroir existe.
9. Horloge : l'installation active `systemd-timesyncd`/NTP ; `rover-live` refuse de démarrer si l'horloge n'est pas synchronisée (`tools/server/ntp_check.sh`, `ExecStartPre`), `sol0ctl status` l'indique.
10. Durcissement (audit du direct) : dossier du flux en `2750 sol0:sol0stream` (setgid : le web lit les fichiers du moteur) ; Caddy sans API d'administration (`admin off`, donc `systemctl restart caddy` et non `reload`, coupure brève) et rechargé dès que le Caddyfile change ; `sol0ctl token set` n'accepte que les jetons à grain fin `github_pat_` ; `X-Forwarded-For` remplacé par Caddy, délais d'en-tête ; SSH : `MaxAuthTries 3`, `LoginGraceTime 30`, pas de X11 ni de redirection TCP, `ufw limit 22/tcp`. Restent hors kit : permissions du jeton (Contents seulement, jamais Workflows), protection de `main` (audit S-4), unité de publication séparée (S-5).

## Page servie par le serveur

Le serveur construit la page du direct à partir du commit déployé (`tools/live/build_page.py`, stdlib seule, sans réseau) et la sert lui-même sur `https://live.EXEMPLE.fr/` (même origine que `/stream`). Jamais de copie à la main. Plan : `out/page-v2/DOMAIN.md`. Non vérifié ici : `caddy validate` (Caddy absent du Mac ; le test `test_caddy_validate_if_available` le lance s'il existe), durée de la coupure du flux au redémarrage de Caddy.

- Étape **S4b** de `install.sh`, séparée de S4 : dossier `/opt/sol0/page-releases/<PAGE_SHA>` (ancien dossier gardé), lien `/opt/sol0/page`. Option `--page-sha COMMIT` (défaut `--sha`) : **déployer une page sans toucher au moteur** (même `--sha`, ni release, ni venv, ni liens `app`/`venv`, ni unités, ni `live.toml`). Ne jamais rattacher la page à la vérification de S4 : elle réinstallerait le venv du moteur vivant.
- Caddy : `/stream /now.json /sol.json /health` inchangés (avant la page) ; page derrière `handle`, `encode` seulement sur la page, fichiers cachés (`.sol0-page`) en 404, `X-Frame-Options`, `frame-ancestors 'none'`, `Cache-Control: no-cache`. Le Caddyfile change une seule fois : un redémarrage de Caddy (`admin off`), coupure brève du flux (les `EventSource` se rebranchent). Les passages suivants avec seulement `--page-sha` ne le changent pas : bascule du lien, instantanée. GitHub Pages garde son CORS (`pages_origin` inchangé, `web.py` non modifié).
- **Déploiement, moteur vivant** : (1) `sol0ctl status`, `curl -s https://live.EXEMPLE.fr/health` ; (2) `install.sh --dry-run ... --sha <SHA MOTEUR ACTUEL> --page-sha <NOUVEAU>` : ne doit lister que la construction de la page, le lien `/opt/sol0/page` et (la première fois) le Caddyfile ; **arrêter** si le plan cite `release-`, `units-enable`, `/opt/sol0/app`, `/opt/sol0/venv`, `live.toml` ou `00-hold` ; (3) appliquer, relancer : « 0 changement » ; (4) contrôler `curl -sSI`, `/config.json`, `/health`, et que `systemctl show -p ActiveEnterTimestamp rover-live` n'a pas bougé. Jamais `sol0ctl birth`, `rover live run`, ni suppression dans `/var/lib/sol0*`.
- **Retour arrière** : page seule : `ln -sfn /opt/sol0/page-releases/<ancien> /opt/sol0/page` (instantané) ou `rollback.sh <UTC>` (relie l'ancien, retire le dossier construit par cette passe, verbe `rmtree` limité à `/opt/sol0/page-releases/` ; une page **reconstruite sur place** (même `--page-sha`) retrouve sa construction précédente, gardée à côté en `<sha>.prev.<UTC>`, verbe `untree`). Caddyfile : `rollback.sh` le restaure mais ne redémarre pas Caddy : `caddy validate --config /etc/caddy/Caddyfile` puis `systemctl restart caddy`.
- **sol0.fr / www.sol0.fr (drapeaux, désactivés par défaut)** : `--site-apex on` ajoute les blocs `sol0.fr` (même page, pas d'API) et `www.sol0.fr` (301 vers l'apex) et le CORS `Access-Control-Allow-Origin: https://sol0.fr` sur l'API de `live.` (origine exacte, pas de joker ; écart avec le plan, qui le liait à `--canonical` : la page de l'apex en a besoin dès qu'elle est servie). `--canonical apex` (exige `--site-apex on`) : la racine de `live.` redirige en 301 vers l'apex, l'API ne bouge pas. Faire en deux temps. Les drapeaux sont gardés dans `/etc/sol0/site.flags` (créé quand on les donne ; un passage sans drapeau les conserve ; **à re-valider**).
- **Garde-fou DNS** : avec `--site-apex on`, `install.sh` refuse (code 1, avant toute modification, même en `--dry-run`) tant que `A` de `sol0.fr` et `www.sol0.fr` ne sont pas exactement ceux de `live.sol0.fr` et qu'un `AAAA` ne correspond pas : sinon Caddy bouclerait sur l'obtention du certificat. À faire par l'utilisateur chez OVH (Espace client, Web Cloud, Noms de domaine, `sol0.fr`, Zone DNS) : `A sol0.fr` et `A www.sol0.fr` vers l'IPv4 de `live`, supprimer tout `AAAA` étranger, désactiver l'hébergement par défaut ; contrôle `dig +short A sol0.fr` ; puis dire « DNS fait ». Ne pas renseigner `sol0.fr` dans Settings, Pages de GitHub.

Non vérifié ici (à faire en L4 sur le vrai serveur) : `systemd-analyze verify`, `caddy validate`, `ufw`, `apt`, nom d'origine du dépôt apt de Caddy pour les mises à jour automatiques. `sol0ctl update|rollback-release|restore|adopt-remote|force-local` : à fournir en L4/L5.
*EN: Direct = install kit in tools/server (dry run, idempotent, rollback); token via `sol0ctl token set`; systemd/Caddy/ufw validated only in L4 on the real server.*

- **Notes après audit (2026-11-13)** : (a) si `site_apex=on` est mémorisé dans `site.flags` et que le DNS échoue un instant, un déploiement de page seule est refusé (sûr, mais bloquant) : `--site-apex off` le contourne. (b) Si un dossier `/opt/sol0/page-releases/<sha>` existe mais est invalide (par exemple construit pour un autre domaine) et que `/opt/sol0/page` pointe dessus, il est reconstruit sur place (courte fenêtre possible) ; cas rare, à éviter en changeant de `--page-sha`. Depuis la correction de l'audit VERIF-S (I1), l'ancien dossier n'est plus effacé : il est mis de côté en `/opt/sol0/page-releases/<sha>.prev.<UTC>` (ligne `NOTE` du kit) et `rollback.sh` le remet ; le kit ne supprime jamais ces copies : les retirer à la main une fois la page contrôlée. Cela vaut aussi pour la première passe de ce lot avec `--site-apex on` sur une page construite par l'ancien kit (sans `<sha>.opts`). Toujours lancer le `rollback.sh` du kit qui a fait la passe : un `rollback.sh` plus ancien ne connaît pas `untree` et s'arrête à cette ligne (« unknown verb »). (c) `SOL0_PAGE_GIT=1` (tests seulement) fait suivre à `--root` le vrai chemin git de la page.

## Sécurité du serveur, lot 1 (2026-11-13, consigne 50)

Ce que le kit fait depuis ce lot (synthèse `out/security/SECURITE-SITE.md`). Rien n'est déployé par ce lot : le déploiement est le Lot 2 (ci-dessous).

- **SEC-01, copie de la vie** : étape S5b, `/var/lib/sol0/repo` devient un clone `--depth 1` de `https://github.com/<dépôt>.git`, fait par `sol0`, **sans identifiant dans l'URL** (le jeton n'est lu que par l'assistant d'identification de `publish.sh`). Les `atlas/ firsts/ journal/` déjà écrits par le moteur y sont recopiés (la version locale gagne : ces dossiers ne font que grandir) ; l'ancien dossier est gardé en `repo.old.<UTC>`, jamais supprimé. Jamais pendant que le moteur tourne (message `WARN`, rien changé). Une origine différente ou avec identifiants : `WARN`, rien changé, l'URL n'est jamais affichée. Étape S5c : lien `/usr/local/bin/python -> /usr/bin/python3` (un autre fichier à cet endroit n'est jamais remplacé). Unité du moteur : `Environment=PATH=/opt/sol0/venv/bin:/usr/local/bin:/usr/bin:/bin`, lue **au prochain démarrage du moteur seulement**. `sol0ctl status` affiche `publish_blocked_since`, `last_publish_s`, la dernière publication (`published.json`) et l'état du clone.
- **SEC-02** : Caddy n'envoie à l'API que GET et HEAD (le reste : 405 de Caddy) et ouvre une connexion neuve vers le service web pour chaque requête (`transport http { keepalive off }`, syntaxe multiligne) : le corps non lu d'une requête ne peut plus être lu comme le début de la suivante.
- **SEC-03** : compte `sol0ops` (mot de passe verrouillé, groupe `sol0` pour lire `live/*.json` ; `secret/` reste en 0700 `sol0`), clé donnée par `--ops-key FICHIER.pub` (clé publique ed25519 ou ecdsa ; une clé privée, deux lignes ou une option injectée sont refusées avant tout changement), écrite `restrict,command="/usr/local/bin/sol0-status"` : pas de shell, pas de pty, pas de redirection ; toute commande demandée est ignorée. `sol0-status` ne fait que lire (services, publication, `/health`, `/now.json`, disque, redémarrage requis, releases, fin du certificat). La connexion root reste permise jusqu'à ce que l'utilisateur change de politique (P-2).
- **SEC-04** : `TasksMax=512` pour `rover-web` (test : au moins `sse_max + reserved_threads + 40 + 8` = 268 avec `config/live/live.toml`).
- **SEC-09** : tiroir `/etc/systemd/system/caddy.service.d/90-sol0-hardening.conf` (NoNewPrivileges, ProtectSystem=strict avec écriture dans `/var/lib/caddy` seulement, filtre d'appels système en EPERM, capacités réduites à CAP_NET_BIND_SERVICE). Si Caddy ne repart pas avec ce tiroir, `install.sh` le met de côté (`.failed`), relance Caddy sans lui et s'arrête en erreur : le site passe d'abord.
- **SEC-15, SEC-29** : la CSP complète part en en-tête HTTP pour la page et pour sa 404 : `default-src 'none'; script-src 'self'; style-src 'self'; img-src 'self' https://raw.githubusercontent.com/<dépôt>/state/; media-src 'self'; connect-src 'self' https://live.<domaine> https://raw.githubusercontent.com/<dépôt>/state/; base-uri 'none'; form-action 'none'; frame-ancestors 'none'; require-trusted-types-for 'script'` (contrat avec la page : même source `state/`, pas de `data:`). `media-src 'self'` seulement : la cinématique d'accueil `media/intro.mp4` ; servie en `video/mp4`, `Cache-Control: no-cache` (nom fixe), Range natif de `file_server`, jamais compressée (`encode` ne cible que les types texte).
- **SEC-17** : `handle_errors` dans `live.` et dans l'apex : mêmes en-têtes de sécurité, pas d'en-tête `Server`, une 404 sert le `404.html` de la page (statut 404 gardé) ; les autres erreurs, un texte court. Le port 80 a ses propres blocs `http://` : 308 vers le même hôte en HTTPS, sans `Server` (les défis ACME HTTP sont traités par Caddy avant toute route : lu dans `modules/caddyhttp/server.go` v2.6.2).
- **SEC-18** : partout ailleurs que GET et HEAD : 405 avec `Allow: GET, HEAD`, avant la page, les fichiers et le proxy (y compris `/robots.txt` et `/.well-known/security.txt`). Exception : `www.` redirige tout (301) vers l'apex.
- **SEC-19** : `Strict-Transport-Security: max-age=31536000; includeSubDomains`. Vérifié avant : la zone ne contient que `sol0.fr`, `www`, `live` et `ftp` (CNAME vers `sol0.fr`, défaut OVH), d'après l'énumération NSEC3 de `out/security/VERIFY-TLS.md` (2026-11-13) ; aucun ne sert de HTTP en clair (FTP n'est pas du HTTP). Pas de `preload` (P-11).
- **SEC-24** : `CPUWeight=1000` (moteur), `CPUWeight=50` et `CPUQuota=100%` (web), `CPUWeight=100` (Caddy, dans le tiroir). Les tiroirs posés à chaud par `set-property` (Lot 0) priment sur ces fichiers : `install.sh` les signale (`NOTE`) et ne les retire jamais.
- **SEC-25** : `ufw` exige `22/tcp LIMIT` sans `ALLOW` restant (l'ancienne règle `ALLOW` est retirée après la pose de `LIMIT`) ; `sshd` : `AllowAgentForwarding no`, `AllowStreamLocalForwarding no`, `PermitTunnel no`, `AllowUsers root sol0ops` (tout autre compte est refusé par SSH : l'ajouter à `tools/server/sshd/10-sol0.conf` avant de s'en servir) ; un fichier `sshd` modifié est toujours rechargé ; `/etc/cloud/cloud.cfg.d/99-sol0.cfg` (`ssh_pwauth: false`) si cloud-init est présent.

## Disque perdu / Disk lost

Principe : la vie du rover **continue** depuis le dernier état publié (branche `state`). L'acte de naissance est recréé **à l'identique, avant** de libérer le moteur : jamais une nouvelle graine, jamais de redépart au sol 0. Ce qui n'a pas été publié depuis la dernière publication (au plus `publish_every_sols` = 24 sols) est perdu, et cela se dit tel quel dans le journal.

À faire dès maintenant, tant que le serveur vit (Diapason, lecture seule) : relever `sha256sum /var/lib/sol0/live/birth.json` et garder une copie de `birth.json` hors du serveur (donnée publique : heure et graine).

1. Nouveau serveur Ubuntu 24.04, clé SSH, DNS (`live`, apex et `www`) vers la nouvelle adresse.
2. `install.sh` au **même** `--sha` que la release du moteur perdu, mêmes drapeaux. `birth.json` étant absent, le tiroir de maintien est posé : le moteur est activé mais **retenu**. Contrôle : `sol0ctl status` dit « RETENU ».
3. `sudo sol0ctl birth-restore --utc <heure de naissance publiée> --seed <graine publiée> [--sha256 <empreinte relevée>]`. La commande recalcule l'acte comme le moteur (`birth.make_record`), refuse si la graine recalculée ou l'empreinte ne correspondent pas, si `birth.json` existe ou si le moteur n'est pas retenu, et écrit un fichier identique octet pour octet. **Jamais `sol0ctl birth`** : il tirerait une graine à l'heure courante.
4. Le clone de publication est refait par `install.sh` (S5b).
5. Adopter l'état publié (à la main tant que `sol0ctl adopt-remote` n'existe pas, Lot 5 ; **non éprouvé**, à exercer sur une autre graine) :
   ```
   sudo -u sol0 git -C /var/lib/sol0/repo fetch --depth 1 origin state
   C="$(sudo -u sol0 git -C /var/lib/sol0/repo rev-parse FETCH_HEAD)"
   N="$(sudo -u sol0 git -C /var/lib/sol0/repo show FETCH_HEAD:state/MANIFEST.json | python3 -c 'import json,sys; print(int(json.load(sys.stdin)["sol"]))')"
   D="/var/lib/sol0/outs/$(printf 'sol-%06d' "$N")"
   sudo -u sol0 mkdir -p "$D"
   sudo -u sol0 git -C /var/lib/sol0/repo archive FETCH_HEAD | sudo -u sol0 tar -x -C "$D"
   printf '%s\n' "$C" | sudo -u sol0 tee /var/lib/sol0/live/published.sha
   printf '{"commit": "%s", "sol": %s, "utc": "%s"}\n' "$C" "$N" "$(date -u +%Y-%m-%dT%H:%M:%SZ)" | sudo -u sol0 tee /var/lib/sol0/live/published.json
   sudo -u sol0 python3 -c 'import json,sys; print(json.load(open(sys.argv[1]))["sol"])' "$D/state/MANIFEST.json"
   ```
   (`sol0ctl verify` ne s'applique pas ici : il recalcule le sol N depuis `sol-(N-1)` et le fichier de flux, absents après une perte de disque.)
6. `sudo sol0ctl release-hold` : refuse si `birth.json` manque ou ne correspond pas à sa dérivation, s'il n'y a aucun `outs/sol-NNNNNN` (N ≥ 1) avec `state/MANIFEST.json`, ou si la publication est active sans `live/published.sha`. Puis `sudo systemctl start rover-live` et `sol0ctl status` ; le flux ne doit montrer aucun événement de naissance.
7. Jeton : il était sur le disque perdu. Le révoquer sur GitHub, en créer un nouveau, `sudo sol0ctl token set`.
8. Instantané Contabo du nouveau serveur.
*EN: disk lost = reinstall at the same engine SHA (engine held), `sol0ctl birth-restore` (identical birth record, checked against the published seed), adopt the published `state`, `sol0ctl release-hold`, start. Never a new seed; the unpublished sols are lost and said so.*
